 What's OAuth and JWT and what is the main difference between OAuth and JWT? // https://supertokens.com/blog/oauth-vs-jwt
 
 OAuth, short for “Open Authorization,” is an open standard protocol that allows secure authorization in a simple and standardized way for web, 
 mobile, and desktop applications. JWT stands for JSON Web Token. It’s an open standard (RFC 7519) that defines a compact and self-contained way for
 securely transmitting information between parties as a JSON object. In other words JWT (JSON Web Token) is a compact, digitally signed token used to
 securely transmit information between a client and a server.A JWT consists of three parts: a header, a payload, and a signature. Header:
 Contains metadata about the token, including the type of token and the hashing algorithm used. Payload: Contains claims (statements about the user)
 and additional data. payload Contains user data, such as:
{
  "sub": "1234567890",
  "name": "Swaminathan",
  "role": "admin",
  "exp": 1735689600
}
 Signature: This is the most critical part for security. Ensures that the token hasn’t been altered. The signature is used to verify that the sender of the JWT is 
 who it says it is and to ensure that the message wasn't changed along the way. o create the signature, you take the encoded header, the encoded payload, a secret
(or private key), and the algorithm specified in the header.
 
 
 JWT Real‑World Example

a) User logs in with username and password
b)Server validates credentials
c)Server returns a JWT token
d)User sends this token on every request
e)Server validates token signature and grants access
 
 Difference 1 - Use Cases and Purpose
 
 OAuth: Primarily used for authorization and delegating access. It’s great when you need to grant third-party applications limited access to user 
 resources without sharing credentials.
 
 JWT: Used for secure information exchange and authentication. It’s perfect for stateless authentication in web applications,especially in microservices 
 architectures.
 
 Difference 2 - Implementation and Complexity
 
 OAuth: Involves a multi-step process with different roles (client, resource owner, authorization server, resource server). It’s more complex but offers
 more flexibility.
 
 JWT: Simpler to implement as it’s self-contained. The token itself carries all necessary information, making it easier to use in stateless applications.
 
 Difference 3 - Security and Management
 
 OAuth: Offers fine-grained access control through scopes. Tokens can be easily revoked, enhancing security.
 JWT: Relies on cryptographic signatures for security. Once issued, JWTs are valid until they expire, which can be a security concern if not managed
 properly.

What is Caching ?

Cache is a part of temporary memory (RAM). It lies between the application and the persistent database. Caching is a mechanism used to increase the 
performance of a system. It is a process to store and access data from the cache. It stores the recently used data. This helps to reduces the number

Can you explain the caching mechanism avaialble in Spring Boot

A Cache is any temporary storage location that lies between the application and persistence database or a third-party application that stores the most
 frequently or recently accessed data so that future requests for that data can be served faster. It increases data retrieval performance by reducing 
 the need to access the underlying slower storage layer. Data access from memory is always faster in comparison to fetching data from the database.
 Caching keeps frequently accessed objects, images, and data closer to where you need them, speeding up access by not hitting the database or any 
 third-party application multiple times for the same data and saving monetary costs. Data that does not change frequently can be cached.

 experience. CDNs cache content like web pages, images, and video in proxy servers near your physical

3. In-Memory Caching

the same page, the content will be delivered from the cache, which helps keep the origin server from getting overloaded. It enhances page delivery speed significantly and reduces the work
needed to be done by the backend server.

Explain Transaction in Spring Boot
Ans: A transaction is a unit of work that must be executed completely or not at all. In Spring Boot, transactions ensure data consistency across operations like 
insert, update, delete—especially when multiple DB operations must succeed together. Spring manages transactions using the Spring Transaction Management Framework, 
usually with @Transactional.

Transactional propagation level in Spring Boot

Spring Transactions Propagation Levels define how transactions should be handled when multiple transactional methods are invoked within a single  transactional
context. These levels allow you to control the behavior of transactional methods, such as whether they should join an existing transaction or create a new one.
Propagation controls what happens to a transactional context when a @Transactional method calls another @Transactional method: Should they share the same 
transaction?. Should the callee start a new transaction? .Should it run without any transaction?

 The Propagation Types
 
 1) REQUIRED (Default)

Behavior: Join existing transaction if present; otherwise start a new one.
Use when: Most business services; you’re fine with a single unit of work across nested calls.
Rollback: If the outer tx rolls back, all inner work rolls back.

2) REQUIRES_NEW

Behavior: Always starts a new transaction; suspends any existing one.


3) SUPPORTS

Behavior: If a transaction exists, join it; else run non-transactionally.

4) MANDATORY

Behavior: Must run inside a transaction; throws IllegalTransactionStateException if none.

5) NOT_SUPPORTED

Behavior: Suspends any existing transaction; runs non-transactionally.

6) NEVER

Behavior: Must run without a transaction; throws IllegalTransactionStateException if one exists.

7) NESTED

Behavior: Start a nested transaction using a savepoint under the existing transaction. If nested part fails, it rolls back to the savepoint, outer tx can still commit.

What is API versioning?

 Ans : API versioning is the process of managing and tracking changes to an API. It also involves communicating those changes to the API's consumers.
 Change is a natural part of API development. Sometimes, developers have to update their API's code to fix security vulnerabilities, while other 
 changes introduce new features or functionality. Some changes do not affect consumers at all, while others, which are known as “breaking changes,” 
 lead to backward-compatibility issues, such as unexpected errors and data corruption. API versioning ensures that these changes are rolled out 
 successfully in order to preserve consumer trust while keeping the API secure, bug-free, and highly performant.
 You should version your API whenever you make a change that will require consumers to modify their codebase in order to continue using the API. 
API Versioning is a defined process of making or managing changes to an API. These changes can be made transparently without
interrupting the clients. When users have permission to decide whether they can conveniently upgrade to the latest version of API and clearly state the changes made is known as a Good 
API Versioning Strategy.

URI Path Versioning : The process of adding the different version numbers like v1,v2, etc. to the API's URL is known as URI Versioning.
Query Parameters Versioning : The process in which version number is passed as a query or request parameter.
Custom Header Versioning : The procedure of adding a custom header to the client HTTP request with version number is known as Custom Header Versioning. This approach keeps the URI Path
clear, but custom header must be included.
Content Negotiation Versioning : Content Negotiation Versioning uses the HTTP Accept header to define the API version. In this method, version is a part of content Negotiation.

Scalability

Scalability ensures that the API can handle increased loads without performance degradation.

1. Efficient Database Design

Indexing & Query Optimization: Properly index database tables to speed up queries
Pagination: Return a limited number of records instead of all (e.g., ?limit=50&page=2).
Caching: Use Redis or Memcached for frequently accessed data.

 Deploy multiple instances of the API behind a load balancer.
 Containerization & Orchestration with Docker & Kubernetes for auto-scaling.

  Offload heavy tasks (e.g., sending emails, processing large data) to message queues like RabbitMQ, Kafka, or AWS SQS.

4. Rate Limiting & Throttling
   Prevent abuse using API Gateway policies or middleware (e.g., Express-rate-limit, Flask-Limiter).
   Implement JWT-based authentication to control user access.

 What are the different scopes of Spring Beans?
 
 singleton (default):
A single shared instance of the bean is created and used throughout the Spring IoC container. This is the default scope if no scope is specified.
Every request for this bean will return the same instance.
prototype:
A new instance of the bean is created each time it is requested from the Spring container.
This scope is suitable for beans that need to be stateless or have a short lifecycle.
request (Web applications only):
A new instance is created for each HTTP request.
The bean is only available during the lifecycle of the HTTP request and is discarded after the request is completed.
session (Web applications only):
A new instance is created for each HTTP session.
The bean is tied to the HTTP session and remains active for the duration of that session.
application (Web applications only):
A single instance of the bean is created for the entire ServletContext (the entire web application).
The bean is shared across all HTTP requests and sessions in the application.
websocket (Web applications only):
A new instance is created for each WebSocket connection.
The bean is tied to the lifecycle of a WebSocket connection and is discarded once the connection is closed.

 What's OAuth and JWT and what is the main difference between OAuth and JWT? // https://supertokens.com/blog/oauth-vs-jwt
 
 OAuth, short for “Open Authorization,” is an open standard protocol that allows secure authorization in a simple and standardized way for web, 
 mobile, and desktop applications. JWT stands for JSON Web Token. It’s an open standard (RFC 7519) that defines a compact and self-contained way for
 securely transmitting information between parties as a JSON object. A JWT consists of three parts: a header, a payload, and a signature. Header:
 Contains metadata about the token, including the type of token and the hashing algorithm used. Payload: Contains claims (statements about the user)
 and additional data. Signature: Ensures that the token hasn’t been altered.
 
 Difference 1 - Use Cases and Purpose
 
 OAuth: Primarily used for authorization and delegating access. It’s great when you need to grant third-party applications limited access to user 
 resources without sharing credentials.
 
 JWT: Used for secure information exchange and authentication. It’s perfect for stateless authentication in web applications,especially in microservices 
 architectures.
 
 Difference 2 - Implementation and Complexity
 
 OAuth: Involves a multi-step process with different roles (client, resource owner, authorization server, resource server). It’s more complex but offers
 more flexibility.
 JWT: Simpler to implement as it’s self-contained. The token itself carries all necessary information, making it easier to use in stateless applications.
 
 Difference 3 - Security and Management
 
 OAuth: Offers fine-grained access control through scopes. Tokens can be easily revoked, enhancing security.
 JWT: Relies on cryptographic signatures for security. Once issued, JWTs are valid until they expire, which can be a security concern if not managed
 properly.

What is API versioning?

 Ans : API versioning is the process of managing and tracking changes to an API. It also involves communicating those changes to the API's consumers.
 Change is a natural part of API development. Sometimes, developers have to update their API's code to fix security vulnerabilities, while other 
 changes introduce new features or functionality. Some changes do not affect consumers at all, while others, which are known as “breaking changes,” 
 lead to backward-compatibility issues, such as unexpected errors and data corruption. API versioning ensures that these changes are rolled out 
 successfully in order to preserve consumer trust while keeping the API secure, bug-free, and highly performant.
 You should version your API whenever you make a change that will require consumers to modify their codebase in order to continue using the API. 
 This type of change is known as a “breaking change,” and it can be made to an API's input and output data structures, success and error feedback, 
 and security mechanisms. Some common examples of breaking changes include:
 
 A) Renaming a property or endpoint: You might sometimes want to rename a property or method so that its meaning is clearer.
 b) Modifying a data format or type: You may sometimes realize that several properties, such as firstName and lastName, should instead exist
   within a user object
 c) Modifying a property's characteristics: You may occasionally be tempted to change the rules for certain properties. For instance, a description 
    property of type: string may have a maxLength rule that you discover is too low or too high.   
	
 What are some types of API versioning?
 
 a) URL versioning: With this approach, the version number is included in the URL of the API endpoint.
 b) Query parameter versioning: This strategy requires users to include the version number as a query parameter in the API request.
 c) Header versioning: This approach allows consumers to pass the version number as a header in the API request
 d) Consumer-based versioning: This versioning strategy allows consumers to choose the appropriate version based on their needs.

 What are the different scopes of Spring Beans?
 
 singleton (default):
A single shared instance of the bean is created and used throughout the Spring IoC container. This is the default scope if no scope is specified.
Every request for this bean will return the same instance.
prototype:
A new instance of the bean is created each time it is requested from the Spring container.
This scope is suitable for beans that need to be stateless or have a short lifecycle.
request (Web applications only):
A new instance is created for each HTTP request.
The bean is only available during the lifecycle of the HTTP request and is discarded after the request is completed.
session (Web applications only):
A new instance is created for each HTTP session.
The bean is tied to the HTTP session and remains active for the duration of that session.
application (Web applications only):
A single instance of the bean is created for the entire ServletContext (the entire web application).
The bean is shared across all HTTP requests and sessions in the application.
websocket (Web applications only):
A new instance is created for each WebSocket connection.
The bean is tied to the lifecycle of a WebSocket connection and is discarded once the connection is closed.

Can you explain connection pooling

Ans : onnection pooling keeps a small, reusable set of database connections “ready” instead of opening a new network connection for every request. Opening/closing 
DB connections is expensive (network handshake, auth, allocation)—a pool amortizes this cost and lets your app serve more requests with lower latency and CPU usage.
By default, since Spring Boot 2.0, the framework uses HikariCP as the default connection pool. It is widely considered the fastest and most lightweight pooling 
library available for Java.

The Lifecycle

Startup: Spring Boot initializes the pool with a set number of idle connections.

Request: When your code needs to talk to the database (e.g., via Repository or JdbcTemplate), it asks the pool for a connection.

Active Use: The application performs the SQL work.

Release: Once the transaction is finished, the connection isn't closed; it’s simply returned to the pool to be reused by another request.

Key Configuration Properties : You can fine-tune how HikariCP behaves in your application.properties or application.yml file. Here are the heavy hitters:

maximum-pool-size,Max number of connections the pool can hold.,10
minimum-idle,Minimum number of idle connections Hikari maintains.,Same as max
idle-timeout,How long a connection can sit idle before being retired.,600000ms (10m)
connection-timeout,Max time a dev waits for a connection before an error.,30000ms (30s)

How to control concurrent updates in rest api

Ans : Concurrency control can be an important part of a REST API, especially if you expect concurrent update requests for the same resource.
While autowiring if two beans of the same type exit, What will the Spring do. One of the biggest API-scaling challenges facing developers is
concurrency control. APIs that are subject to a high volume of unsafe requests must be designed with control strategies that can gracefully
handle situations when multiple requests attempt to update a single resource. 
API clients commonly perform updates by retrieving a copy of a resource, manipulating it locally, and posting the updated resource to its
associated endpoint. This pattern is fine for low volumes of requests but things can become more complicated when multiple clients retrieve
the same version of the resource. In that case, both clients make their respective changes locally and post the resource. Whichever request
is written last overwrites the other request’s version of the resource, causing changes to be lost.
Example if User1 and User2 gets a ressouce at the same time. Firtsly User1 update it. In a few seconds if User2 also update the resource, the
change of User1 lost. 
 
To deat with thisn issue we can use Etag(tokens) : In a pessimistic locking scheme, the client locks a resource for exclusive use until it 
is finished updating the resource. Pessimistic locking is generally undesirable for REST API development. It forces the server to maintain 
state, a big REST no-no. It also complicates the design of the client and raises the possibility of deadlocking. 
In a pessimistic locking scheme, the client locks a resource for exclusive use until it is finished updating the resource. Pessimistic locking
is generally undesirable for REST API development. It forces the server to maintain state, a big REST no-no. It also complicates the design
of the client and raises the possibility of deadlocking. 

An ETag is an identifier for the version of the underlying resource. It can be implemented using a hashing algorithm or using a version numbering
scheme. It is also possible to use a timestamp for an ETag, though this is generally not recommended since machine clock times may be skewed 
across the distributed servers that back your API. The key quality of a good ETag scheme is that it produces a different ETag for each version
of the resource. 

To use make a request using optimistic concurrency, the client application first retrieves the resource that it wishes to update and stores the
 ETag that the server returns with the response body. The client application then performs any relevant updates and POSTs the resource back with
 the If-Match condition header and the ETag that it retrieved previously. If the ETag matches the resource’s current ETag, the server performs
 that update and responds with success. Otherwise, the server rejects the update with a 412 Precondition Failed response.

How multithreading is being implemented in spring boot?

Ans : 1) Declarative Multithreading with @Async : Gemini said
In Spring Boot, multithreading is primarily implemented through an abstraction called the TaskExecutor. While Java provides the low-level Thread class, Spring Boot manages concurrency at a higher level using thread pools and, in modern versions, Virtual Threads.

Here is how multithreading is implemented across different layers of a Spring Boot application.

1. The Core Abstraction: TaskExecutor
The TaskExecutor interface is the heart of Spring's multithreading. It is a simplified version of Java’s java.util.concurrent.Executor. When you run a task asynchronously, Spring doesn't just "create a thread"; it delegates the task to a bean implementing this interface.

ThreadPoolTaskExecutor: This is the most common implementation. It wraps a Java ThreadPoolExecutor, allowing you to configure a Core Pool Size, Max Pool Size, and Queue Capacity.

How it works: When a task arrives, Spring tries to use an idle "core" thread. If they are busy, the task goes into a queue. If the queue is full, Spring creates "max" threads.

2. Declarative Multithreading with @Async
The easiest way to implement multithreading is using the @Async annotation. It tells Spring to execute the method in a separate thread.
Enable it: Add @EnableAsync to your main configuration class. Annotate it: Add @Async to a method in a @Service or @Component.
Return type: Asynchronous methods usually return void or CompletableFuture<T>.
Example :

@Service
public class EmailService {
    @Async
    public CompletableFuture<String> sendEmail(String user) {
        // This runs in a background thread from the pool
        return CompletableFuture.completedFuture("Email sent to " + user);
    }
}

What is a secret manager ?

Ans : A Secret Manager is a secure system for storing and retrieving sensitive information such as passwords and API keys. It prevents hard‑coding
secrets in applications and provides encryption, access control, audit logging, and automated rotation of secrets. A Secret Manager is a tool or
 service used to securely store, manage, and access sensitive information such as:

Passwords
API keys
Database credentials
OAuth tokens
Certificates
Encryption keys

Instead of hard‑coding secrets in your code or configuration files, you store them in a centralized, encrypted vault and access them securely at
 runtime.

Avoid hardcoding secrets in code (prevents exposure in GitHub, logs, etc.)
Centralized management of all sensitive values.
Automatic rotation of passwords, API keys, and certificates.
Fine‑grained access control (only specific apps/users can read secrets).
Audit logs to track who accessed secrets and when.
Encrypted at rest and in transit → increased security.

How to read data from a secret manager ?
Ans :

Reading data from a Secret Manager depends on which cloud provider or tool you're using (AWS, Google Cloud, Azure, or HashiCorp Vault). However,
the general workflow is almost always the same: Authenticate → Request → Parse. Here is a breakdown of how to handle this for the most popular
 services.
 
 What is rate limiting ?
 
 Ans : Rate limiting restricts the number of requests a user or system can make to an API within a defined time window (e.g., 100 requests per
 minute). If the limit is exceeded, the server blocks or delays further requests.
 
 How to restrict api access ?
 
 Ans : Restricting API access is about moving from a "wild west" setup to a Zero Trust model. You want to ensure that only the right people, 
 using the right devices, can access the right data.
 
 1. Authentication (Who are you?)
This is the first gate. You must prove your identity before the API even looks at your request.

API Keys: Simplest method. A unique string passed in the header. Best for internal tools or low-security public data.

OAuth2 / OpenID Connect: The gold standard for user-facing apps. Users log in via a provider (Google, GitHub, Auth0), and your API receives a JWT (JSON Web Token).

mTLS (Mutual TLS): High-security "handshake" where both the client and the server must present a valid certificate. Common in microservices or banking.

2. Authorization (What can you do?)
Just because I'm "logged in" doesn't mean I should be able to delete your database.

RBAC (Role-Based Access Control): Assigning permissions to roles (e.g., Admin, Editor, Viewer).

Scopes: Limiting what a specific token can do (e.g., read:profile vs. write:settings).

ABAC (Attribute-Based Access Control): More granular. Access is granted based on attributes like time of day, IP address, or department.

3. Network-Level Restrictions
If you know exactly where your traffic is coming from, you can lock the door at the network layer.

IP Whitelisting: Only allow requests from specific, trusted IP addresses.

VPC Peering / Private Links: If your API and your app are both in the cloud (AWS/GCP/Azure), you can keep the traffic entirely off the public internet.

CORS (Cross-Origin Resource Sharing): A browser-level security feature that restricts which domains (e.g., myapp.com) are allowed to call your API.

4. Traffic Control & Shielding
This protects your API from being "hugged to death" or attacked.

Rate Limiting: As discussed, this prevents abuse by capping requests per user/IP.

Web Application Firewall (WAF): A filter that sits in front of your API to block common attacks like SQL injection or Cross-Site Scripting (XSS).

API Gateways: Tools like Kong, AWS API Gateway, or Apigee act as a single entry point that handles auth, logging, and rate limiting for you.
