 Deadlock in Java Threads
 
 Ans: A deadlock in Java occurs when two or more threads are waiting indefinitely for each other to release locks on resources.
 This creates a situation where no thread can proceed, resulting in a system freeze. Deadlocks usually happen when:
 A thread locks Resource A and waits for Resource B. Another thread locks Resource B and waits for Resource A. Neither thread can
 proceed because they are both waiting on each other.

   What is ConcurrentHashMap and Hashtable? In java, why is ConcurrentHashMap considered faster than Hashtable?
   
   Hashtable locks the entire table during a write operation, thereby preventing other reads or writes. This could be a bottleneck 
   in a high-concurrency environment. ConcurrentHashMap, however, allows concurrent reads and limited concurrent writes, making it 
   more scalable and often faster in practice. ConcurrentHashMap: Utilizes a fine-grained locking mechanism (or lock striping) that
   allows multiple threads to access different segments of the map concurrently. This reduces contention and improves throughput in 
   scenarios with many concurrent operations. ConcurrentHashMap: Divides the map into segments (or buckets), each of which can be 
   locked independently. This allows for concurrent updates and reads across different segments, enhancing performance in 
   multi-threaded applications.
   
   How ConcurrentHashMap works internally and what are it's main features.
   
   ConcurrentHashMap internally uses HashTable as its data structure. It is thread safe just like Hashtable. It provides all the functionalities 
   of HashMap except thread safety. ConcurrentHashMap internally divides it into segments. Each segment works independently and can be accessed by 
   different reader threads simultaneously. However, each segment can be accessed only by one writer thread at a time. The default level of concurrency 
   is 16. Which means by default, there are 16 segments. Read operations don’t require locking of cocurrent hash map, where as write operations do require
   locking. Locking is known as segment or bucket locking. Concurrent hash map doesn’t allow null key or null values. 
   
   ConcurrentHashMap returns a fail safe iterator. It means, using this iterator, we can modify ConcurrentHashMap while iterating. Each segment works
   as an individual HashMap. So, if one thread is writing onto one segment, it locks that segment. Now until that thread is done, no other thread will
   get access to that segment. However, reader threads can still access this segement. If another thread, wants to write to another segment at the
   same time, it is free to do so. It will acquire lock on that segment and will start doing its job. Read operations return most recently updated 
   operations, which means the it may not fetch the currently updating value.

  Why Overriding equals() and hashCode() in Java
  
  equals() and hashcode() are by default present in Java super class java.lang.Object.
  Overriding equals and hashCode is crucial when working with collections. Collections like HashSet, HashMap, or Hashtable rely on the
  hashCode method to organize and search for objects efficiently.  If we don’t override equals and hashCode correctly, these collections
  may not function as expected. Objects that should be considered equal might not be properly identified, leading to duplicates in sets
  or incorrect retrieval from maps. Two objects are considered equal only if their references ponits to the same object. unless we override
  equals() and hashcode() method, the class object will not behave properly on hash-based collections like HashMap, HashSet and  HashTable
  This is because hash based collections are organized like a sequence of buckets  and hash code value of an object is used to determine
  the bucket where the object would be stored and the same hashcode value of an object is used again to find the object position in the 
  bucket. The key retrieveal is basically a two step process.  Finding the correct bucket using hashcode and linearly searching the bucket
  for the key using equal().Overriding equals() without overriding hashCode() causes the two equal instances to have unequal hashcode. which
  violate the hashcode contract.

  What changes were done for HashMap in Java 8	
  
  In Java 8, HashMap replaces linked list with a binary tree when the number of elements in a bucket reaches certain threshold. When the number of elements in a bucket exceeds a certain
  threshold (called TREEIFY_THRESHOLD, which is 8), the linked list is converted into a balanced binary tree (specifically a red-black tree).This reduces the lookup time for that bucket
  from O(n) to O(log n). If the number of elements drops below another threshold (UNTREEIFY_THRESHOLD, which is 6), the tree is converted back to a linked list.

 What is Future in Java?

Default Methods:

Purpose:
Default methods were introduced to allow for the addition of new methods to existing interfaces without breaking compatibility with classes that already implement 
those interfaces. They provide a "default" implementation that implementing classes can either use directly or override.
Access:
Default methods are instance methods. They are inherited by implementing classes and can be called on instances of those classes, similar to regular instance methods.
Overriding:
Implementing classes can override default methods to provide their own specific implementation, if desired.
Keyword:
Declared using the default keyword. 
Static Methods:
Purpose:
Static methods in interfaces are similar to static methods in classes. They are utility or helper methods that belong to the interface itself, not to any specific 
instance of an implementing class. They are useful for providing common functionality related to the interface that does not depend on the state of an object.
Access:
Static methods are accessed directly through the interface name, not through an instance of an implementing class. For example, InterfaceName.staticMethod().
Overriding:
Static methods in interfaces cannot be overridden by implementing classes. They are part of the interface's definition and are not inherited in the same way as 
instance methods.
Keyword:
Declared using the static keyword.


Local cache : Local cache refers to a cache that resides in the same JVM (Java Virtual Machine) or process as your application. This is sometimes known as an 
"in-memory" cache because the cached data is stored in the main memory of the server running the application. The primary advantage of local caching is speed.
Since the cache is in the same memory space as your application, accessing this data is extremely fast. Another benefit is simplicity; such systems are easier 
to implement and manage because they do not require network configuration or additional dependencies.

Distributed Cache : Distributed cache, on the other hand, is a cache shared over multiple nodes/servers. It provides a solution to both the scalability problem 
and the data inconsistency issue intrinsic to local caches. A distributed cache can handle much larger data volumes because it spreads data across multiple nodes.
It also maintains data consistency across different instances of your application by ensuring that all instances refer to the same cache. However, distributed caches
are generally slower than local caches because they often require network calls to retrieve data. They're also more complex to set up and  manage due to the networking
requirements

Why was finalize() deprecated?

finalize() was deprecated starting from Java 9 because it was considered unreliable, unsafe, and harmful for performance

Unpredictable Execution
The Garbage Collector decides when (or if) to call finalize().
There is no guarantee that it will run promptly or even at all before the program exits.
Performance Issues
Objects with finalize() take longer to collect because they require an extra GC cycle.
This can lead to memory leaks and increased GC overhead.
Risk of Resurrection
Inside finalize(), an object can make itself reachable again (called object resurrection), which complicates GC and can cause bugs.
Better Alternatives Exist
Resource cleanup should use try-with-resources and AutoCloseable instead of relying on GC.

Does  Java supports global variables ? why/why not

Ans: Java does not support true global variables like languages such as C or C++ 
Reason
Object-Oriented Design:
Java is designed around the principle of encapsulation and object-oriented programming. Global variables would break encapsulation by allowing unrestricted access to data across the 
entire application.

Namespace Pollution:
Global variables can lead to naming conflicts and make code harder to maintain. Java avoids this by requiring variables to be declared within classes or methods.

Thread Safety & Security:
Global variables can cause concurrency issues in multi-threaded environments and pose security risks. Java promotes controlled access through class fields and methods.

Time slicing and preemptive scheduling in Java

Time Slicing

Definition:
Time slicing is a CPU scheduling technique where each thread/process gets a fixed time slice (quantum) to execute. After its time expires, the CPU switches to the next thread in the ready 
queue.
Purpose:
Ensures fairness among threads so that no single thread monopolizes the CPU.
In Java:

Java threads rely on the underlying OS scheduler for time slicing.
The JVM does not guarantee strict time slicing; it depends on the platform.
Example: Multiple threads running with Thread.yield() can hint the scheduler to give up CPU, but actual slicing is OS-controlled.

 2. Preemptive Scheduling

Definition:
Preemptive scheduling means the CPU can forcibly take control from a running thread and give it to another thread with higher priority or when its time slice expires.
Difference from Non-Preemptive:

In non-preemptive, a thread runs until it voluntarily releases the CPU (e.g., completes or waits).
In preemptive, the scheduler can interrupt a thread at any time.

In Java:

Java uses preemptive, priority-based scheduling for threads.
Higher priority threads are favored, but not guaranteed (depends on OS).
The JVM maps Java thread priorities to OS thread priorities.

what is the life cycle of a thread

New (Created)

When you create a thread using Thread t = new Thread(); but haven’t started it yet.
The thread object exists, but it’s not running.
Transition to Runnable happens when you call t.start().

Runnable

After calling start(), the thread is ready to run but waiting for CPU time.
It’s in the ready queue, and the OS scheduler decides when it runs.
Methods like yield() can influence scheduling.

Running

When the thread gets CPU and executes its run() method.
Only one thread per CPU core can be in Running state at a time.

Blocked / Waiting

Blocked: Waiting to acquire a lock (e.g., synchronized block).
Waiting: Waiting indefinitely for another thread to signal (via wait()).
Timed Waiting: Waiting for a specific time (e.g., sleep(ms), join(ms)).

Terminated (Dead)

After run() completes or the thread is stopped.
Cannot restart a dead thread (calling start() again throws IllegalThreadStateException).

Two differne types of type casting

1. Primitive Type Casting
This involves converting one primitive data type into another.
It can be of two kinds:

a)Implicit (Widening) Casting:
Happens automatically when converting a smaller type to a larger type.

int num = 10;
double d = num; // int to double (widening)

b) Explicit Casting (Narrowing)
Done manually by the programmer when converting a larger type to a smaller type.

double d = 10.5;
int num = (int) d; // double to int (narrowing)

2. Reference Type Casting
This involves converting one object type into another within the same inheritance hierarchy.
It can be of two kinds:

a) Upcasting
Converting a subclass object to a superclass type.
Done implicitly. 
Example
class Animal {}
class Dog extends Animal {}
Animal a = new Dog(); // Upcasting

b)Downcasting

Converting a superclass reference back to a subclass type.
Requires explicit casting and usually checked with instanceof.
Example:

Animal a = new Dog();
Dog d = (Dog) a; // Downcasting
